# Failure modes — what happens when X fails

| Failure | What happens | Why it's safe |
|---|---|---|
| **Redis is completely flushed or restarted** | Rate limiting resets (fails open — briefly more permissive, never less). Realtime WebSocket updates pause until the outbox worker's next successful publish. **Seat holds, bookings, idempotency, and payments are entirely unaffected** — none of them read from Redis. | Postgres is the sole source of truth for anything that must not be lost. Redis only accelerates rate limiting and pub/sub fan-out. |
| **Worker process crashes mid-sweep** | The next tick — from the same process after restart, or a second worker instance — re-queries Postgres for bookings past `expires_at` and finishes the job. A booking that was mid-expiry (seat freed, booking not yet marked EXPIRED, say) is simply picked up again; the operations are safe to retry because each seat-freeing UPDATE only touches rows still owned by that booking (`WHERE held_by_booking_id = :booking_id`), so re-running it on an already-freed seat is a no-op. | `expiry_worker.sweep_once` locks each candidate booking row with `SELECT ... FOR UPDATE SKIP LOCKED` before acting on it, so a second concurrent worker instance skips rows already being processed rather than double-processing them. |
| **A seat hold's TTL elapses while a payment is in flight** | The booking moves `PAYMENT_PENDING -> EXPIRED` via the same sweep. If the payment webhook later reports SUCCEEDED, `booking_service.handle_webhook` detects the booking is EXPIRED and attempts to re-acquire the same seats; if they're still free, the booking is resurrected to CONFIRMED, otherwise the payment is marked REFUNDED and the booking stays EXPIRED. | See `docs/design.md` §6 and `tests/failure_injection/test_payment_webhooks.py`. |
| **Duplicate payment webhook delivery** | The second (and any further) delivery for the same `provider_ref` is detected via `payment.status != PENDING` and is a pure no-op (`"already_processed"`). | Payments are looked up by `provider_ref` (unique), and the booking row is locked with `SELECT ... FOR UPDATE` before any state change, so concurrent duplicate deliveries serialize instead of racing. |
| **Out-of-order webhook (FAILED arrives after SUCCEEDED for the same ref)** | Same mechanism as above — once `payment.status` leaves `PENDING`, every later webhook for that `provider_ref` is a no-op regardless of what status it claims. | A payment's terminal status, once set, is never overwritten by a stale delivery. |
| **Client retries a mutating request (network blip) with the same Idempotency-Key** | Exactly one concurrent request actually runs the handler (via `INSERT ... ON CONFLICT DO NOTHING` on the idempotency_keys PK); every other request with that key returns the identical cached response. A retry with a *different* body under the same key is rejected (422) rather than silently mismatched. | `app/services/idempotency_service.py`; the claim table lives in Postgres, so it survives a Redis outage too. |
| **Two users submit overlapping multi-seat hold requests simultaneously** | Whichever request's transaction commits first wins every seat it can; the other gets a 409 listing exactly which of its requested seats were unavailable — never a partial hold. | Deterministic lock ordering + conditional UPDATE per seat, same transaction. See `test_multiseat_hold_is_all_or_nothing`. |
| **Postgres itself goes down** | The API returns 5xx / the `/readyz` endpoint reports `database: false` and the whole service is correctly marked not-ready (e.g. for a load balancer health check). No writes are silently lost or accepted — everything routes through the same transactional session. | There is no write path that bypasses Postgres. |
| **A hot show's admission-token JWT is replayed for a different user or show** | Rejected — `queue_service.verify_admission_token` checks the token's embedded `show_id`/`user_id` claims match the request, not just that it's a validly signed token. | Prevents someone sharing an admission token to let a friend skip the queue on a different account or show. |
| **The mock payment provider never calls back at all (simulated "timeout")** | The booking stays `PAYMENT_PENDING` until its hold TTL elapses, at which point the expiry worker moves it to `EXPIRED` exactly like any other timed-out hold. If the "timed out" payment eventually does succeed very late, it hits the late-success reconciliation path above. | Timeouts are not a special case — they're just "no webhook arrived before the TTL," which the existing expiry sweep already handles. |
